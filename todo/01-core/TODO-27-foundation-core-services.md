## Outcome

- `isotone::core::AppFolders` resolves each app's data root and its `logs`, `settings`, and `recovery` folders under `%LOCALAPPDATA%\Rizonesoft\<App>\` (beside the executable in portable mode), creating them on first use.

## 2. Atomic File Writes and the Settings Store

> **Started:** 2026-11-13T07:48:10Z

**Fidelity:** no surface of its own (non-feature infrastructure: a foundation mechanism with no competitor-facing feature of its own, so no `**Exceed:**` paragraph; the product sections that use it carry theirs) -- a core service.
**Needs:** Windows host (build/test)

Every later section's settings persist through this store, and a change writes one line to the audit log of §1.

**Corrected 2026-11-13** (pre-build validation, each fact measured that day): (1) **The JSON library is nlohmann/json** (vcpkg port `nlohmann-json` 3.12.0 at the committed baseline, MIT, header-only), the register decision `standards/shared.md` ("Settings and JSON") leaves to the first section that needs one. Reason: it is the most widely used C++ JSON library, fuzzed continuously in OSS-Fuzz and tracked by OSV, its parser and its destructor are iterative (deep nesting cannot overflow the stack), and being header-only it adds no library to link, no CRT question, and no architecture difference. yyjson and simdjson are faster, which a settings file of a few kilobytes never needs; glaze is younger. It is included only by `native/core/src/settings.cpp`, never by a public header, so replacing it later costs that one file. It is registered in `docs/dev/native-libraries.md` and added to `native/vcpkg.json` in this section's commit. (2) **The settings file is `<settings folder>\settings.json`**: `standards/shared.md` ("Document safety") said `%LOCALAPPDATA%\Rizonesoft\<App>\settings.json`, written before §1 shipped the `settings` folder; the stamped folder wins, the standard's line is corrected in this commit, and the files kept aside sit beside it. (3) **Two writers.** Two processes of one app may write the same file, and without mutual exclusion each would read back the other's bytes and "restore" over them, so a write and a settling read hold a lock file (`<name>.lock`, opened with no sharing and deleted on close, so a dead process never leaves it held), waiting at most `AtomicFileOptions::lock_wait` (2 seconds by default) before reporting; under the lock the temporary file is `<name>.tmp` and the backup `<name>.bak`, so a file a crash left is overwritten or settled by the next call, never accumulated. A plain read with no backup present takes no lock and writes nothing, so an app run from a read-only folder still reads its settings. (4) **Which copy wins after a crash.** "Whichever holds the newer verified contents" is made exact: the target wins when it exists and passes the caller's check (it always passes when the caller gives none: its bytes were verified before they took the name); otherwise the backup is restored. (5) **A backup that cannot be deleted** after the target has read back correct is not a failed write: the new contents are in place, and the next read removes the backup; the item said "any failure after the replace". (6) **Readback reads the device, not the cache**: a readback through the handle that wrote the bytes only reads the file cache back, so both readbacks reopen the file with `FILE_FLAG_NO_BUFFERING`, falling back to an ordinary read only where the file system refuses unbuffered access. (7) **Settings merge on write**: `set` re-reads the file under the lock and applies only the keys it changes, so two processes of one app never lose each other's settings; a `set` of the value a key already holds writes nothing and logs nothing; a failed write leaves the value in memory unchanged and reports. (8) **The settings reader is a file reader** (`standards/cpp.md`, "Untrusted input"): the file is limited to 4 MiB, checked before anything is allocated, and it has a fuzz target, `settings`, with a corpus and a regressions folder. (9) **Values** are `bool`, a 64-bit integer, a finite `double`, and a UTF-8 string; a value of any other JSON type that a file already holds is kept through a rewrite and read as the default. A setting never holds a credential, because every change is logged with its value.

**Added 2026-11-13** (plan review, D01-T27-S2-PR1 to PR4): a write limit equal to the read limit, a settling check that accepts any version, the move-aside decision under the lock on a fresh read with collision and refusal handling, and an explicit contract for a failed restore.

**Added 2026-11-13** (second plan review, on the built candidate `69834b5`, D01-T27-S2-PR5 and PR6): (1) recovery no longer depends on the caller knowing the format: before the replace a journal, `<name>.txn`, records the size and FNV-1a checksum the target must hold, flushed, and it stays until the target has read back correct and the backup is gone; a later read or write keeps the target exactly when it holds the journal's bytes and otherwise restores the backup, so a target that is wrong but well formed is never chosen and a reader with no check loses nothing; the check rule of correction (4) remains only for a backup with no journal beside it; the journal reader has its own fuzz target, `atomic_file_journal`. (2) A set that is refused for size moves nothing aside: the size of what would be written is checked before an unusable file is moved.

**Added 2026-11-13** (round 1, D01-T27-S2-R1-1 to R1-4): a backup already beside the target when a write starts is never overwritten (it stays what a failed write goes back to); whole numbers are compared as signed values in range, never through the library's mixed-sign comparison; a key given more than once in one set takes its last value and is compared and logged once.
