# TODO-14 -- Foundation: Runtime Theming from the Design Tokens

> **Goal:** `isotone::ui` exists as a static library, and every value a native surface draws with comes from token tables generated from `docs/design/tokens.json`, resolved at run time for the current theme, Highlight, density, and high-contrast state, so a style names a token key and never a value, and switching any of them, or Windows changing high contrast, reduced motion, or DPI, redraws exactly what read the changed keys.

## 1. The isotone::ui Library and the Generated Token Tables

> **Started:** 2026-11-13T14:34:03Z

The library starts here because tokens are the first thing any surface draws with. The tables are generated, never hand-edited, so the design page and the native code can never disagree about a value.

**Fidelity:** no surface of its own (non-feature infrastructure: a foundation mechanism with no competitor-facing feature of its own, so no `**Exceed:**` paragraph; the product sections that use it carry theirs) -- a library target and generated tables; the surfaces that draw with them are later sections'.
**Needs:** Windows host (build/test)

**Corrected 2026-11-13** (pre-build validation against `docs/design/tokens.json`, `docs/design/README.md`, and `docs/design/components/Highlight/README.md`, each fact measured that day): (1) **The Windows accent table is not generated**: it is computed at run time from `UISettings` by the Highlight service (`docs/design/components/Highlight/README.md`, "Windows accent mapping"; owned by `D01 T01 §3`), so this section generates the Blue values (the `state*` tokens, in the brightness tables) and the Isotone orange mapping (each `state` key to its `state-orange` token, `glow-state` to `glow-state-orange`), defines the shape a computed table has (`HighlightColors`: `state`, `state-hover`, `state-pressed`, `state-on`, `state-subtle`, `state-tint`, `state-line`, `state-text`, and the color of `glow-state`), and resolves the Windows accent choice from a table the caller supplies, falling back to Blue when there is none, as the design says. The item said the generator writes a Windows accent table. (2) **The high-contrast mapping is not in `tokens.json`**: it is a prose table in `docs/design/README.md` ("Windows high contrast") that names token groups and leaves 25 of the 71 color tokens unnamed (`state-hover` and `state-pressed`, the eight `state-orange*` tokens, `text-placeholder`, the two scroll thumbs, `border-control-hover`, `border-popup`, `ruler-surface`, the scrim, `selection-inactive`, the four status colors, and the three caption close tokens). The design is the source, so this section first writes the complete mapping into `tokens.json` as `color.highContrast` (every color token to a system color, to `keep` for the canvas colors that show the user's content, or to `none` for a fill that is dropped) and completes the README table from it. **Default** for each token the README did not name, recorded there: hover and pressed states follow their rest state; `text-placeholder` is `COLOR_GRAYTEXT`; scroll thumbs and every border are `COLOR_WINDOWTEXT` (hover: `COLOR_HIGHLIGHT`); `surface-control*` is `COLOR_BTNFACE` (the README's "buttons"); the scrim, the app accents, and the status subtle fills are `none`; status colors are `COLOR_WINDOWTEXT` (the icon and the word stay); the caption close button is `COLOR_HIGHLIGHT` with `COLOR_HIGHLIGHTTEXT`; changing one later is an edit to `tokens.json` and a regeneration. (3) **System colors are an input, not a call**: resolving under high contrast needs the eight system colors; `Theme` takes them in its state (`SystemColors`), and reading them with `GetSysColor` on `WM_SETTINGCHANGE` is §2's, so this section's library calls no window API and its tests need no display. (4) **Every token type is typed**, not only the three the item named: colors (sRGB bytes and linear floats, with the 256-entry conversion table generated so a run-time color converts the same way), sizes, spacing, and radii in DIPs, durations in milliseconds, the easing curve as its four control values, shadows (offset, blur, color per theme), type styles (family, size, line height, weight, and letter spacing in DIPs), and the three font family lists. (5) **Aliases stay aliases**: `icon`, `focus-ring`, and `handle-stroke` name another token (`{text-secondary}`, `{state-line}`, `{state}`), and the table keeps the reference, so a Highlight or high-contrast change to the target reaches them. (6) **Density keys**: `tokens.json` has only the `-compact` and `-comfortable` values; the generator adds the neutral key for each pair (`control-h`, `row-h`, `type-body`, and for type styles `caption`, `body`, `body-strong`), which resolves by density, and the two explicit keys stay addressable. (7) **The value check reads the source**: a test with a hand-copied sample would repeat the generator's own reading, so `Theme.ValuesMatchTokensJson` parses `docs/design/tokens.json` itself at test time and compares every token of every type in every theme with what the tables resolve. (8) **Generated files and the gates**: both files start with the generated mark and `// clang-format off`, so the format gate leaves them as the generator wrote them, and they must pass clang-tidy and `/analyze` like any source.

**Added 2026-11-13** (plan review, D01-T14-S1-PR1 and PR2): (1) the type styles of the Compact density are named `caption`, `body`, and `body-strong` in `tokens.json`, with no `-compact` name, so the rule of correction (6) is made exact for both kinds: a size pair `X-compact` and `X-comfortable` gains the neutral key `X`; a type style `X` that has an `X-comfortable` sibling keeps `X` as the neutral key and gains the explicit key `X-compact`, which holds the values `tokens.json` gives `X`. Either way the three keys exist, the neutral one resolves by density, and the explicit ones never change; the duplicate-name refusal applies to the source names and to a generated key that would collide with one. ## 2. Run-Time Resolution and Live Switching, Proved in the Host

A style reads keys, so a change of theme, Highlight, density, or a Windows signal is a change of resolved values, and only the styles that read a changed key are invalidated. The proof runs in the foundation test host, whose placeholder panels draw with tokens.

**Fidelity:** no surface of its own (non-feature infrastructure: a foundation mechanism with no competitor-facing feature of its own, so no `**Exceed:**` paragraph; the product sections that use it carry theirs) -- the switching mechanism, proved on the test host's placeholder panels; product surfaces bind their own Design lines.
**Needs:** Windows host (build/test)
**Requires:** display-session -- convicted by docs/specs/2026-10-22-native-stack-design.md, "Element tree and theming" (the switch is proved in a live window)

Each theme, Highlight, density, or contrast change writes one line to the host's audit log, and setting the previous value again reverses it exactly, so the change needs no undo entry of its own.
