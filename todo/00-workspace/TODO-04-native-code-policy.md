# TODO-04 -- The Native-Code Policy, Its Gate, and the Benchmark Harness

> **Goal:** The suite's answer to "C#, C, or C++?" is written down once, enforced by a gate, and backed by measurement: C# is the language of every app and library; native code enters only as a mature third-party library, a Windows system API, or an own kernel that a committed benchmark record shows the best managed and GPU paths cannot match; every native call goes through source-generated `LibraryImport` over a flat C ABI (never `DllImport`, never C++/CLI); every file-format reader the suite writes itself stays managed; and a BenchmarkDotNet harness produces the dated records that admission bar, the pixel engine, and every later "is it fast enough" question cite.

> [!IMPORTANT]
> **Current state (verified 2026-09-30):** The operator asked on 2026-09-30 whether developing in C# loses optimization against C or C++ and whether the languages can be mixed, then accepted the recommendation above ("yes, add all to the todos, sounds good"). Nothing in the tree uses native interop yet: no `DllImport` or `LibraryImport` in any C# source, and no C or C++ source or `.vcxproj` anywhere. The heavy paths already lean on native code or the GPU through packages: SkiaSharp (Skia, C++) and ComputeSharp (C# compiled to HLSL on DirectX 12) in `Directory.Packages.props`. The plan already brings in many native libraries through `LibraryImport`, each with its own ad hoc rules: lcms2 in `D01 T04 §1` (the first, with the convention `tools/native/<lib>/build.ps1`, `SOURCE.txt` with the source hash, binaries under `runtimes/<rid>/native/`, and a `THIRD-PARTY-NOTICES.md` entry), then libmypaint, OpenColorIO through a C shim, libwebp, OpenEXR, PDFium, libjpeg-turbo, DjVuLibre, and CharLS in the Gesso and Albumen parity files, and LibRaw in `D04 T01 §3`; no standard states the convention, so each section re-derives it. `standards/gesso.md` asks for SIMD with a scalar path and "a benchmark names the budget before an optimization lands", but there is no benchmark project and no place a benchmark result is recorded. Gesso's tiles are managed `byte[]` rented from `ArrayPool` (`src/Gesso/src/Gesso.Core/Tiles/Tile.cs`). There is no `docs/dev/decisions.md` yet; `D00 T02 §5` creates it.

## 1. The Native-Code Standard, the Register, and the Native-Lint Gate

The operator decided on 2026-09-30 that the suite stays C#-first and mixes in native code only by rule. The rule must exist before the first native library lands (`D01 T04 §1`, Phase 6), or every section that adds one keeps inventing its own conventions, and a gate must hold it, or the rule decays into prose. The reasons the standard records: the hot paths are already native or GPU (Skia, ComputeSharp, and the planned decoders); modern .NET reaches C++ speed within a small factor in tight loops with `Span<T>`, `Vector<T>`, and `System.Runtime.Intrinsics`, but does not auto-vectorize, so SIMD is written by hand; a flat C ABI through `LibraryImport` is cheap per call and keeps the build simple, while C++/CLI ties the build to MSVC mixed mode; and parsing untrusted files is the suite's largest attack surface, where managed bounds checks are worth more than the last few percent of speed. This section must not change any build output: it adds documents and a read-only gate.

- [ ] Write `standards/native-code.md` with these headings: "The rule" (C# for every app and library; native code only as one of the three admitted kinds; the operator decision of 2026-09-30 quoted), "Admitted kinds" (a Windows system API; a mature third-party library with a register row; an own kernel that passed the admission bar), "Calling native code" (`[LibraryImport]` only, `DisableRuntimeMarshalling` where the bindings allow it, blittable structs with explicit `StructLayout`, `SafeHandle` for every native resource, one call per tile, row, or buffer and never per pixel, callbacks only through `[UnmanagedCallersOnly]` where a library requires them, no C++/CLI, a C++-only library reached through a flat C shim under `tools/native/<lib>/shim/`), "Building and shipping" (`tools/native/<lib>/build.ps1`, `SOURCE.txt` with the upstream URL, tag, source SHA-256, and compiler version, binaries under `src/<project>/runtimes/<rid>/native/` for `win-x64` and `win-arm64`, the license in the project's `THIRD-PARTY-NOTICES.md`, a GPL-3.0 compatibility check, signing with the app), "Untrusted input" (every file-format reader and writer the suite writes itself is managed C#; ## 2. The Benchmark Harness and the First Benchmark Record

`standards/gesso.md` already says a benchmark names the budget before an optimization lands, and §1's admission bar for an own native kernel is a benchmark record; neither can be met without a harness and a record format. BenchmarkDotNet is the .NET standard for this (MIT, statistically sound warmup and iteration, memory diagnostics, hardware-intrinsic job control), so it is added as a recorded dependency. The first record answers the operator's question with a number on this machine: how close managed SIMD gets on the suite's hottest kind of loop, a per-pixel premultiply over one 256-pixel tile, which is also the baseline `D01 T03 §1` builds from. Benchmarks are not tests: they never run under `dotnet test`, and only a smoke mode that checks correctness runs in the gates.

- [ ] Add `BenchmarkDotNet` to `Directory.Packages.props` at the latest stable version on nuget.org on the day (quoted in the commit), and record the dependency in `docs/dev/decisions.md` (MIT license URL, developer-only, never shipped in an app, the alternative of hand-rolled `Stopwatch` loops rejected for no warmup, no outlier handling, and no allocation data). Done when: the props file names the package and the decision entry names its license and this section.
- [ ] Create `tests/Isotone.Benchmarks/Isotone.Benchmarks.csproj`: an `Exe` on the solution's target framework with `AllowUnsafeBlocks`, `IsPackable` false, `IsTestProject` false, no reference to any app project, and add it to `Isotone.slnx`.
