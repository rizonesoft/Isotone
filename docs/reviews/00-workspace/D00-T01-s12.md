## Self-review

1. Does it make sense? `scripts/merge_prs.py` merges at most one green Dependabot or pins pull request per run by rebase, bound to its head (`--match-head-commit`), its base, and `origin`'s github.com repository, never a .NET SDK pin, a rename, or a pull request whose expected workflows have not completed green on its head. It runs only when the clone is on a clean `main` level with the freshly fetched `origin/main` and no section is in progress, judged after the fetch and again right before the merge; it pulls, checks the merge commit landed on `main`, and runs `validate`. The loop calls `run --campaign` after each stamp push's green read-back, campaign start and resume call `recover` (which never merges) and read both workflows back, and the hourly `isotone-pr-merge` task calls `run --task`.
2. Is it logical? Once a merge is issued, only a verified merge clears its intent record; every other outcome keeps it and exits 3, and any later run resolves the record from GitHub's state before anything else (merged and landed with a clean level tree and a green validate clears it; open or closed clears only after the 15-minute settling window, three times the 300-second command bound). Exit 1 means the merge was never issued, exit 2 a refused preflight, and the scheduled run maps a busy clone to exit 0 so its failure email fires only on a real failure. One merge run holds `build/merge-prs.lock` at a time, and the scheduled run also holds the run guard's lock and refuses an active campaign before touching recovery.
3. Did it break anything else? `check-all` gains gate 20 and `plan-gates` a step for the 55 tests; the automations README, `AGENTS.md`, `process-phase`, `process-plan`, `process-todo-section`, and `review-todo-section` state the rule and the both-workflow read-back; `tasks.json` gains `isotone-pr-merge`, and the automations tests pass with it. No app code changed.

The same-family circuit breaker fired once: after rounds 12 and 13 each found the clone judged before a slow call and trusted after it, the preflight was reordered (the fetch first, every local check back to back after it) instead of adding another check. A person editing the working tree is not something a lock can exclude; the design narrows that window and re-checks before the pull. `source-defect` and `design-fidelity` lenses not owed beyond the independent pass's `source-defect` lens.
