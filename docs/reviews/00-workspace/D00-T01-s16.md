## Self-review

1. Does it make sense? The unattended merger can no longer fall silent. A guarding workflow on `main` that has not read green for two hours alerts (exit 1), timed per workflow across heads in `build/merge-prs-health.json` and cleared only by a green read. Every merge the script makes stays unverified until its own commit's CI is read: every later `run` and `recover` reads it first, pending holds every merge, and a red, no evidence, or a merge unread two hours on is exit 1. A busy clone (uncommitted work, a detached checkout, a section in progress) still reports a red `main`, judged on the fetched `origin/main`, never the checkout. An older run is never inherited across a change to its workflow's own file, and a failed observation moves no record.
2. Is it logical? One judgment (`judge`) reads `main`'s verdicts, runs the preflight, and only then ages the timers on `main`'s own head, so the checkout never speaks for `main`. Inheritance follows GitHub's own rule: each push compared at its endpoints through `main`'s push activity, every commit's paths when that chain cannot be followed, and the workflow file read at the judged head. The merge read (`_merge_verdict`) uses no newest-runs window: own runs by commit, a cancelled run decided by the first finished successor among every run since, and with no own run the merge's own push decides. `unknown` (no run history) reads as red and moves nothing.
3. Did it break anything else? The D00 T01 §15 cases all pass (two were updated to give `main` its own green head, because a busy task now reports a red `main`, which is this section's item 3), the boundary merger and `recover` keep their exit codes with one addition (exit 1 for an unread or red merge), named in `process-plan` and the automations README, and `test_automations.py` and the campaign guard self-test pass. No app code changed.
