## Self-review

1. Does it make sense? Every `run` of `scripts/merge_prs.py` now judges `main`'s own CI through `judge`: it reads each guarding workflow (`plan-gates`, `build`) by its push run on `main`'s head, or for a path-filtered one by an older run on an ancestor whose later changes miss its push paths, then runs the preflight, requires the same head, and only then reports. Running or still to come is a busy clone (exit 0 with `--task`, 2 otherwise); completed without success, or no run history, is exit 1 naming the run. It runs before the listing and again right before the merge, so the hourly task never merges onto a red `main` and its next run reports a red its own merge caused. A detached checkout (symbolic-ref's own exit 1 with HEAD resolving) is a busy clone.
2. Is it logical? Nothing local is judged across a GitHub read: CI first, then the fetch and the local checks back to back, then the verdict. A red is never reported for a clone the preflight refuses. The trigger reader is a whitelist that fails closed: any shape it does not fully know means the workflow runs on every change, which both callers read the cautious way (a pull request must show the workflow; an older run never stands in for the head's), and does-not-run is answered only from an `on:` block read in full.
