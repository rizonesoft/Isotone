## How to read this spec

Everything marked **Default** is a justified default: the choice this spec makes so work can start, its reason, and its cost of changing. The operator can overturn any of them in review. **Open questions** at the end need the operator's call before the re-plan. ## Goals and how each is measured

### The reference environment

All performance numbers are measured on one recorded reference machine and display (**Default**: the development machine, its CPU, GPU, driver version, RAM, storage, Windows build, display resolution, scaling, and refresh rate written into `docs/dev/reference-machine.md` by the first benchmark section, and re-recorded when any of them changes), with the app's Release build, a fresh profile, and the fixtures named below.

### The goals

| Goal | Target at each app's first native release | Protocol |
| ---- | ----------------------------------------- | -------- |
| Cold start | Main window accepting input in under 500 ms at the median and under 800 ms at the maximum of 10 runs | Each run after a reboot and a 60 s idle, with the cold condition made by construction rather than checked: the run launches a fresh copy of the app's publish folder, written to a new folder with unbuffered I/O (`CopyFile2` with `COPY_FILE_NO_BUFFERING`), so no page of the app's own files has ever been in the file cache or mapped by another process, and no prefetch trace names that path; SysMain (which can preload an app's pages, as Microsoft's startup measurement guidance warns) is stopped for the runs. Because a scanner or indexer can still read or map the copy before launch, the harness records file I/O with Windows Performance Recorder from the copy to the launch and discards the run if any other process read or mapped the app's files in between. The harness waits for the main window to exist, sends a scripted keystroke at once, and times from the process creation time (`GetProcessTimes`) to the displayed frame that shows the keystroke's effect (presentation statistics), both in the same system-time units, so a window that is drawn but not yet answering input does not stop the clock; 10 runs, median and maximum reported |
| Warm start | Under 250 ms at the median of 10 runs | The same endpoint, launching the installed app after it has run once |
| Interface frame cadence | At the display's refresh rate, no more than 1 missed vsync per 1,000 frames, and no single gap longer than two vsync intervals | 60 s each of panning, zooming, panel resizing, and window resizing on the fixture documents, with displayed-frame times taken from presentation statistics (`IDXGISwapChain::GetFrameStatistics` and PresentMon), not from renderer timings |
| Pen latency | For 95 percent of pen samples, under one refresh interval plus 4 ms from the sample's input timestamp to the first displayed frame that shows it; none over two refresh intervals plus 4 ms | Every sample is measured, not only the newest: the coalesced history of each pointer message (`GetPointerInfoHistory`) gives every sample's `QueryPerformanceCounter` timestamp (`POINTER_INFO.PerformanceCount`); each presented frame records the samples it drew and its present id, and presentation statistics give the vsync it was displayed on, in the same clock domain. A sample merged into a later one counts at the later one's display time; a dropped sample counts as a failure. Physical pen-to-photon latency is not claimed; a later section may add a hardware measurement |
| Output size | Each app's publish folder at or under 30 MB before optional content (operator answer) | `scripts/publish.ps1` reports the size and a gate fails over budget; exceeding it needs a decision entry, never a quiet increase |
| Dependencies | The executable imports only Windows system DLLs; every library is linked statically and registered | A gate reads the executable's import table (`dumpbin /dependents`) and the dependency register |
| Work lost to a crash | The saved file never; unsaved work at most the edits since the last checkpoint (see Document safety) | The crash tests in Document safety |

The fixture documents (a small, a typical, and a large document per app, the large one at the plan's documented limits) are committed with the first benchmark section.

## The toolchain

- **Language:** C++23 compiled by MSVC with `/std:c++23preview` (operator remark 2026-10-22, "Looks like C++ 20 is not the latest"; `docs/dev/decisions.md`, 2026-10-22: The C++ language standard). The rule is the newest standard that MSVC offers a standard-scoped switch for, never `/std:c++latest`, which adds in-progress and experimental features: the pin moves to `/std:c++23` when MSVC ships it, and to C++26 when MSVC ships a switch scoped to that standard, each move a section that rebuilds and retests everything. Microsoft documents that preview features "may change and may not be ABI compatible across releases"; that is contained here because the toolset is pinned and every library is linked statically and built by that same toolset, so a toolset move rebuilds the whole program, and clang-tidy and clang-format run in their C++23 mode. The exact toolset version is pinned (below), not "whatever is installed". Modules are not used yet (**Default**: headers until MSVC, CMake, and clang-tidy handle modules together without workarounds; changing later is mechanical).
- **Build description:** CMake, with Ninja as the generator for scripts and CI and committed `CMakePresets.json` (Debug, Release, and the sanitizer configuration, for x64 and ARM64), which Visual Studio opens natively (**Default**; the alternative is the Visual Studio generator driving MSBuild from the same `CMakeLists.txt`, which changes the presets' generator, not the build description).
- **Pinning the toolchain:** Ninja cannot select a toolset by itself, so `scripts/dev-env.ps1` locates Visual Studio with `vswhere`, enters its developer environment for the pinned MSVC toolset (`-vcvars_ver`) and Windows SDK version and the target architecture, verifies `cl`'s reported version and the SDK, and refuses a mismatch; the presets use the external toolset strategy and every script and CI job runs inside that environment. CMake, Ninja, the LLVM tools (clang-tidy, clang-format), and the vcpkg tool are pinned to exact versions separately from the vcpkg ports baseline, each checked by a gate. The pinned toolset is one the CI runner image provides (Visual Studio Professional 2026, 18.11, with Windows SDK 10.0.26100 is installed on the development machine; the pin is chosen where both meet).
- **Runtime:** the static C runtime (`/MT`), so no Visual C++ redistributable is installed with an app.
- **Packages:** vcpkg in manifest mode with a committed baseline, using the static triplets for x64 and ARM64, plus a sanitizer triplet that builds dependencies with AddressSanitizer so the sanitizer configuration covers library code as well as ours.
- **Architectures:** x64 and ARM64 from day one (operator answer). ARM64 is cross-compiled on x64 for every build, and its tests run on an ARM64 Windows machine (a CI runner of that architecture, or a recorded local ARM64 machine if none is available), so cross-compiling is never mistaken for running.
- **Warnings and analysis:** `/W4 /WX /permissive-`, MSVC `/analyze` on CI, clang-tidy with a committed configuration, and clang-format checked by a gate, the C++ equivalents of today's warnings-as-errors and `dotnet format` gates.
- **Tests:** GoogleTest through CTest (**Default**: the most widely supported C++ test framework with CTest and Visual Studio; changing is mechanical per file).
- **Fuzzing:** every file reader has a fuzz target, built with libFuzzer. MSVC's `/fsanitize=fuzzer` is documented as experimental, so the first fuzzing section qualifies it against the pinned toolset and, if it falls short, builds the fuzz targets with clang-cl instead (a recorded decision either way). Each target keeps a committed seed corpus and every crashing input as a regression case under `native/tests/fuzz/<reader>/`; CI runs each target for a fixed budget (**Default**: 5 minutes per target per night) with `-rss_limit_mb` and `-timeout` limits, and the regression inputs on every build.

## The architecture

### Sharing, reconciled with the plan's decisions

The suite's rule is that shared code is built only when two apps need it. The plan already records operator exceptions built ahead of their second consumer (`todo/01-core/INDEX.md`): the pixel engine, color management, the AI core, the pixel engine extensions, and the develop engine. This spec keeps every one of them as a shared library, so the raster pixel engine and color management are shared from the start, not owned by Gesso as the first draft said.

Building a whole UI toolkit of our own is new, and its consumers are all three apps by construction: there is no version of this decision in which Stilus has its own toolkit and Gesso another. So `isotone::core` and `isotone::ui` are shared from the start, by the operator's answer of 2026-10-22 ("Share fro mthe start, but the apps should be installable seperately also"). Shared means shared source and build targets, never a shared install: the libraries are static, each app's executable links its own copy, and no app installs, loads, or requires another app or a common runtime, so each still installs and runs alone. Within them, the existing rule still holds piece by piece: a control or service is added when the first app needs it, never speculatively.

### Isotone Core (`isotone::core`)

The non-UI foundation every app links: app-data paths; settings stored as JSON with atomic writes and readback; structured logging (one line per action that changes a document or a setting); the command registry (every command once, with its id, label, shortcut, and enabled state, the single source the menus, shortcuts, command search, and layout maps read); undo and redo as recorded commands; document safety (below); the task system (below); atomic file I/O; localization services (below); crash diagnostics (below); and the update check.

### Isotone UI (`isotone::ui`)

Our own interface toolkit, drawn to `docs/design/` with nothing in between. It is the largest new piece of work, and each part a general-purpose framework would hand us has its own section with its own proof.

- **Windows and frames:** Win32 windows with per-monitor DPI awareness (v2) and layout in device-independent pixels rounded to physical pixels at every scale; the Isotone title bar drawn by us with the menu bar inside it (DWM frame extension, and hit testing that keeps Windows 11 snap layouts on the maximize button).
- **Rendering:** one Direct3D 11 device per process with Direct2D and DirectWrite over it, and DirectComposition: each window's interface is one visual with its own swap chain, and the document canvas is another visual with its own swap chain, so the two redraw independently (**Default**: Direct3D 11 for maturity and Direct2D interoperability; Direct3D 12 only where a measured engine need requires it).
- **Swap chains and partial redraw:** composition swap chains use `DXGI_SWAP_EFFECT_FLIP_SEQUENTIAL` (not `FLIP_DISCARD`, which does not support partial presentation) with `Present1` dirty and scroll rectangles. Because flip-model back buffers rotate, the renderer tracks each buffer's accumulated damage and redraws the union since that buffer was last presented. Tests alternate disjoint invalidations, scrolling, resizing, and occlusion and compare every presented frame with a full redraw.
- **Device loss:** every GPU resource is owned by a renderer that can rebuild it from CPU-side state. On device removal or reset (`DXGI_ERROR_DEVICE_REMOVED` or `DXGI_ERROR_DEVICE_RESET` from a present or a call), the renderer releases the device, recreates the device, the Direct2D and DirectComposition objects, the swap chains, and every resource, and redraws; documents live in CPU memory or the tile store, never only in video memory. Direct2D's own recovery signal is handled the same way: `D2DERR_RECREATE_TARGET` from `EndDraw` or `Flush` recreates the target and its device-dependent resources. If hardware initialization fails, the app runs on the WARP software device with a notice. Tests force device removal (the Direct3D debug layer's removal or `dxcap -forcetdr`), inject `D2DERR_RECREATE_TARGET` through a test hook in the renderer, and start on WARP with the hardware adapter hidden, each proving the documents intact and the app usable.
- **Display color:** a shared display color pipeline, owned by `isotone::ui` for all three apps. Each monitor's color mode is read with `DisplayConfigGetDeviceInfo`: the `DISPLAYCONFIG_DEVICE_INFO_GET_ADVANCED_COLOR_INFO_2` query where Windows provides it, which distinguishes ordinary SDR, Advanced Color SDR (wide color gamut, including Auto Color Management), and HDR, and the older `..._GET_ADVANCED_COLOR_INFO` query elsewhere, whose limits the section records; `IDXGIOutput6::GetDesc1` supplies the luminance range but is not used to tell the modes apart. In ordinary SDR the window's swap chain is 8-bit and documents are converted from their profile to the monitor's ICC profile with LittleCMS. In Advanced Color SDR and in HDR the swap chain is FP16 in scRGB (`DXGI_FORMAT_R16G16B16A16_FLOAT` with `DXGI_COLOR_SPACE_RGB_FULL_G10_NONE_P709`) and documents are converted to scRGB, because under Advanced Color Windows changes how ICC profiles apply (Microsoft's Advanced Color and HDR guidance). Luminance has an explicit policy per mode, because Windows interprets scRGB 1.0 differently in each (Microsoft's Advanced Color guidance: display-referred on SDR, scene-referred on HDR). In HDR, the interface and every SDR document are drawn with their white at the user's SDR reference white level (`DISPLAYCONFIG_SDR_WHITE_LEVEL`, scaling linear values by that level over 80 nits), never at scRGB's nominal 80 nits. In Advanced Color SDR, scRGB 1.0 already means the display's white, so no reference white scaling is applied. An HDR document (a float document with an HDR profile) is shown with its highlights tone-mapped to the display's peak luminance on an HDR display, and tone- and gamut-mapped to SDR white on an ordinary or Advanced Color SDR display, by one defined operator (**Default**: the ITU-R BT.2390 EETF). The pipeline re-reads the mode when a window moves to another monitor, when the display configuration changes (`WM_DISPLAYCHANGE`), and when its DXGI factory reports it is no longer current (`IDXGIFactory1::IsCurrent`), and switches its swap chain format without a wrong frame. Proofs: color patches measured through the pipeline against a known profile in ordinary SDR, in Advanced Color SDR, and in HDR; an SDR document on an HDR display at the reference white; an SDR document on an Advanced Color SDR display at the display's white, unscaled; an HDR document on an SDR display; and a window moved between monitors in different modes.
- **Element tree and theming:** a retained tree of elements with measure and arrange layout, invalidation, and dirty-rectangle redraw. Design tokens are resolved at run time from tables generated from `docs/design/tokens.json` (one per theme, Highlight, and density, plus the high-contrast mapping), so a style names a token key and never a value; switching theme, Highlight, or density, or Windows changing high contrast (`WM_SETTINGCHANGE`), reduced motion (`SPI_GETCLIENTAREAANIMATION`), or DPI, invalidates the styles that read the changed keys and redraws. This is the native equivalent of the design contract's `DynamicResource`, and layout rounding replaces WPF's: the design contract's exact values and 1 DIP tolerances carry over unchanged, and its WPF-named mechanisms are renamed to these equivalents in the re-plan. design-lint moves to the C++ sources.
- **Controls:** every component in `docs/design/components/` (buttons, inputs, number boxes, sliders, menus, context menus, tabs, lists and trees, the tool rail, the options bar, panels, dialogs, tooltips, toasts, the status bar), one set the apps share.
- **Docking:** our own docking system (panels, tab groups, columns, floating windows, and the saved workspace as JSON), with the layout maps' Panels part as its default.
- **Input:** keyboard focus and commands; pointer input through `WM_POINTER` for mouse, pen (pressure, tilt, barrel button), and touch; the wheel and precision touchpad.
- **Text:** one shared text editing model under every text box and the apps' type tools: grapheme-cluster-aware caret movement and deletion, bidirectional caret and selection, undo grouping, and font fallback through DirectWrite's system fallback; layout with DirectWrite. Input methods go through the Text Services Framework with a text store (`ITextStoreACP2`) that implements its lock protocol and reentrancy rules, composition start, update, commit, and cancel, focus changes during composition, and candidate-window placement at mixed DPI. Proofs: Chinese, Japanese, and Korean composition sessions driven through the real IMEs; Arabic and Hebrew caret and selection; combining sequences and emoji; and text on a transformed canvas.
- **Accessibility:** a UI Automation provider for every element, with the control patterns each control needs (Invoke, Toggle, Value, RangeValue, Selection and SelectionItem, ExpandCollapse, Scroll, Text, and Grid where they apply), the properties and the focus, selection, structure, and text events, fragment navigation, virtualized items for long lists, and a stated provider lifetime and threading rule (calls arrive on any thread and are answered from the UI thread's state). UI Automation tests read and invoke the tree, but because invoking through UI Automation bypasses the keyboard, pointer, hit testing, and IME paths, those paths have their own tests: keyboard and mouse through `SendInput`; pen pressure, tilt, and barrel button, and multi-touch, through synthetic pointer injection (`CreateSyntheticPointerDevice` and `InjectSyntheticPointerInput`), with a recorded check on real pen hardware for each release; and input methods by driving a real IME's composition (the Windows Japanese, Chinese, and Korean IMEs active, keystrokes through `SendInput`, composition events observed), never by injecting committed text. Named screen reader scenarios (Narrator, and NVDA) are run as driven checks with their transcripts recorded.
- **Desktop exchange:** shell file and folder dialogs (`IFileOpenDialog`, `IFileSaveDialog`, with each app's file types); the clipboard through OLE with delayed rendering, each app's formats (its own, plus PNG, SVG, and text as its sections define), and ownership released safely at exit; drag and drop through OLE (`RegisterDragDrop` after `OleInitialize`); and printing on two paths: ordinary printing through Direct2D's print control (`ID2D1PrintControl`) with the Print Document Package API, covering printer capabilities, page settings, cancellation, and color handling; and prepress jobs the app writes itself (Stilus's own PostScript for a RIP, with in-RIP separations and trapping, and its own PDF, `D02 T13 §10`) sent unchanged to the queue as a raw job through the spooler (`OpenPrinter2`, `StartDocPrinterW` with the `RAW` datatype, `WritePrinter`), only to a queue whose driver or PPD accepts that language, because Direct2D print control consumes drawing commands and cannot carry an app's own page description. The existing per-app clipboard and printing sections keep their feature scope and are rewritten onto these contracts.
- **Localization:** translated resources per app, with plural and gender rules and locale-aware number, unit, and date formatting and parsing through the ICU that ships with Windows (`icu.dll`, a system component); right-to-left interface layout with mirroring; mnemonics and shortcuts that survive translation; and a pseudo-localization build (longer strings, accented characters, right-to-left) that the gates run. These foundations exist before controls and command labels become fixed interfaces.

### Threading and lifetimes

- **The UI thread** of each process is an OLE single-threaded apartment (`OleInitialize`). It owns every window, the element tree, Text Services Framework, the UI Automation providers' state, drag and drop, and the clipboard, and it is the only thread that changes a document: commands run there and are recorded for undo.
- **The GPU:** the Direct3D 11 immediate context is used from one thread at a time. A render thread owns it and does every draw and present, and the UI thread hands it immutable render snapshots (the element tree's draw list and the document's visible tiles at a version). Because the immediate context is shared and its submissions are asynchronous, GPU engine work is cut into bounded dispatches (**Default**: each under 2 ms of GPU time on the reference machine) that the render thread interleaves with interface and canvas frames, interface frames first, and the work queued ahead of a frame is bounded too: the render thread submits the next engine dispatch only when fewer than a fixed number are unfinished on the GPU, tracked with event queries (`D3D11_QUERY_EVENT`) (**Default**: one), so no backlog of short dispatches can stand between an input sample and the frame that shows it. A test runs a filter that would enqueue hundreds of dispatches while measuring pen latency and frame cadence. Each swap chain is waitable with a maximum frame latency of 1 (`IDXGISwapChain2::SetMaximumFrameLatency`), and only the newest pending snapshot per visual is kept, so neither a slow frame nor a backlog of snapshots adds latency. Direct2D is created multithread-protected where the canvas and the interface share it. The frame cadence and pen latency goals are verified while a GPU filter and background work run, with floating panel windows open.
- **Engines** read immutable document snapshots (copy-on-write tiles and geometry), so background work never sees a half-applied edit. A result never overwrites newer work: every task records its document's identity and the edit version it started from, and its result is committed as a command on the UI thread only if the document is still open and still at that version; otherwise the result is discarded, and re-run if it is still wanted (a preview), or reported (an applied filter the user started and then edited past). Tasks hold the document weakly, so a late callback after the document closed finds nothing and does nothing. Tests: a filter that completes after another edit, after an undo, after cancellation, and after the document closed.
- **Tasks** run on a thread pool in three priority classes: interactive (what the user is waiting on, bounded so a frame is never starved), background (previews, thumbnails, indexing), and idle. Every task is cancellable, and a document's tasks are cancelled before it closes.

### Document safety

The failure model: the process can die at any instruction (a crash, or a hang the user ends), and the machine can lose power at any moment. No code is assumed to run after the failure, so recovery never depends on a crash handler.

- **Saving is held to seven invariants.** This spec owns the invariants and the proofs; the document safety foundation section owns the exact call sequence, reviewed there with its code and proved by the tests below, and a sequence that cannot meet an invariant sends this spec back for revision. The protection boundary is the user account, as Windows draws it: processes running as the same user can open one another and read their memory, so a restriction narrower than the account (a DACL naming only one logon session) is carried on the document itself by the file identity contract but is not a boundary the app's process, its secondary copies, or DPAPI can enforce against another session of the same account. The invariants therefore defend against crashes and power loss at any instant and against the ordinary concurrent programs a document's file meets (an external editor saving it, sync clients, antivirus scanners and indexers holding it open, the user in Explorer), not against a program running as the same user that sets out to defeat them, which can read and write the app's own memory and so defeat any protocol. The guarantees are about files: data in storage a file no longer occupies (freed clusters, an SSD's remapped blocks) is outside any application's control, and full-volume encryption such as BitLocker is what protects it. The user guides say both. (1) After any crash or power loss and the next start's recovery, the target's name holds a complete old or new version; for a save to a name that held no file, it holds the complete new version or nothing. (2) The new data is never in a file under protection broader than the target's: the temporary file's protection is derived from the target's own before any data is written (for a name that held no file, from the folder's inherited protections, as any new file there would get), a save that cannot reproduce the target's protection (the file identity contract, next) is refused, and a protection another program adds to the target while the save runs (a tightened DACL, a new EFS key holder, encryption itself) reaches the new file before the save is reported, with the user told that it arrived mid-save. (3) A save deletes, releases, or moves a file only through a handle it opened and has held since, with sharing that lets no other program write, rename, or delete that file: the temporary file from its creation, and the previous version from before the save moves it aside. So the file it removes is exactly the one it created or checked, proved by holding it rather than by inspecting its contents, file times, or file IDs (which FAT can change on rename), and no other program can write either file's data or rename or delete it while the save runs. Sharing modes apply per stream and do not cover attributes (Microsoft's `CreateFileW` and File Streams documentation), so another program can still attach a named stream or an extended attribute, as sync clients do; deleting the app's own temporary file removes such metadata with it, which loses no document data. Whether the previous version is the one the app last read or wrote is decided by hashing its data while it is held; one that is not is kept, as a conflict. Recovery holds no such handle, so it never deletes or overwrites anything: it completes what it safely can and lists every leftover file for the user. (4) Saves of one target commit in edit order: a save requested while another runs waits, and only the newest waiting request runs. (5) A failure before the commit point fails the save with the previous version in place. (6) Every state a later step depends on (the commit, each applied contract item, the release of the previous version) is durable on the medium before that step, not merely readable back from the cache, and the journal records each durable state, so recovery resumes from the last one and never needs a file an earlier step released. (7) A step after the commit that cannot complete safely, such as a protection that cannot be applied, rolls the save back (the previous version restored to the target's name and the new file deleted through the handle held since its creation, since the document stays open with its edits and its encrypted checkpoints) rather than leave the new file weaker or a copy of it under weaker protection; when restoring would overwrite a file, the conflict outcome applies. Invariants 5 and 7 concern a target that held a file; a failed first save to a new name leaves that name empty. One state is pending rather than final, and is the only exception to invariants 2 and 7: after a crash, when recovery cannot yet apply a protection or roll back because another program holds the committed file open, the weaker file stays where it is with the journal record kept, the user is told which file is not yet protected and where the previous version is, and recovery completes it once the handle is released. A save the app reported as successful never left a weaker file. Two conflicts have fixed outcomes, which the proofs check. When the version at the target's name is not the one the app last read or wrote (another program changed or replaced it before the save moved it), the save completes, that version is kept under a named path, and the user is told; a version another program overwrote in place was destroyed by that program, which no save can prevent. When a file appears at the target's name while the save is installing the new data, the save does not complete, every version is kept under a named path (the previous version, the other program's file at the target's name, the new data), and the user is told where each is.
- **The save sequence** is designed in the document safety foundation section against those invariants, and its review rounds start from the requirements the spec's own review established (rounds 3 to 10 in `docs/reviews/independent/2026-10-22-native-stack-spec.md`): no lock is held on an open document's file, so other programs keep reading and writing it (Albumen's viewer hands images to an external editor, `D04 T04`), and the app watches the file's folder (`ReadDirectoryChangesW`) and offers to reload when another program changes it (**Default**); every read and write of a document computes its SHA-256 through CNG as the bytes pass, so the app knows the content hash of the version it last read or wrote with no extra read; the temporary file takes a fresh random name created with `CREATE_NEW`, and files are released only through held handles (invariant 3), so another program holding the target open for writing makes the save fail before its commit, with a message; renames never replace, so a displaced file is moved aside and never destroyed; the journal names every file and records every durable state; and `ReplaceFileW` is not used, because its documented failure cases can leave neither name in place, it does not support write-through, and it preserves less than the contract (DACLs, but neither the integrity label nor EFS key holders). The guarantee is stated for local NTFS and ReFS volumes; on FAT, exFAT, and network shares the same sequence runs and the log records the weaker durability of their renames.
- **The file identity contract** is the one list of what a save carries from the version it displaces to its replacement. A save checks before writing document data that it can reproduce every item for the target as it stands, and is refused with a message naming the item when it cannot; every item is applied, made durable, and read back before the previous version is released, bound to the version actually displaced (invariants 2, 6, and 7), so a save never weakens a file's protection: the owner where the user may set it; the DACL; the mandatory integrity label with its policy (read and written with `LABEL_SECURITY_INFORMATION`); the security resource attributes; the creation time; the file attributes (a read-only target is refused, never overwritten); compression; EFS encryption with every user able to decrypt the target (`QueryUsersOnEncryptedFile` on the target, `AddUsersToEncryptedFile` on the empty temporary file, refused when a user's certificate is unavailable; recovery agents follow the machine's policy as for any encrypted file); and the target's other named data streams (such as the Mark of the Web). Outside the contract, as with every replacing save, and stated in each user guide: audit entries in the SACL (readable only with `SeSecurityPrivilege`), extended attributes, the file ID and object identifier, and other hard links to the target, which keep the previous version.
- **Secondary copies** of document data never rest on disk weaker than the document, up to the user-account boundary stated under Saving. A secondary copy is every file an app writes that holds document content and is not the document itself: checkpoints, crash dumps, the tile store's scratch spill, persisted undo data, and preview and thumbnail caches, and any new kind a later section adds joins this list in that section. Each is encrypted before its first byte is written, with AES-GCM through CNG, whatever the source document's protection, and written into a folder created with a DACL granting only the user and SYSTEM; the encryption is the protection that always holds, and the DACL is a second layer that a volume without access control lists (FAT and exFAT, such as a portable copy on a USB drive) cannot carry, which the log records. A checkpoint is readable only by the user who wrote it (DPAPI's user scope, which a roaming profile carries to that user's other machines, as Microsoft's `CryptProtectData` remarks describe), so recovery under another account reports that the recovery data there cannot be read instead of offering it; the recovery folder itself is under the local, non-roaming app data, so checkpoints follow the user to another machine only in a portable copy. Copies that must outlive the process (checkpoints, crash dumps, preview and thumbnail caches) use a per-file key wrapped with the user's DPAPI key (`CryptProtectData`); copies that serve only the running process (the tile store's scratch and persisted undo data) use a key held only in that process's memory, so after a crash they are unreadable and the next start deletes them. The save journal holds paths and counters, never document data. The frame cadence, pen latency, and tile store figures are measured with this encryption on.
- **Checkpoints:** each open document, untitled ones included, is checkpointed to the app's recovery folder with the same write, flush, and verify steps, encrypted as Secondary copies says, alternating between two slots so a corrupted or interrupted checkpoint always leaves the previous good one; each checkpoint carries a checksum, the document's persistent identity, the session's identity, and the document's edit counter. **Default** cadence: a checkpoint starts within 10 s of the first unsaved edit, and then whenever there are unsaved edits and 60 s have passed since the last completed checkpoint or the user has been idle for 5 s. The bound is stated against completed, durable checkpoints: a crash loses the edits since the newest checkpoint that finished writing and flushing. When no checkpoint has completed for 120 s while edits are unsaved (a slow disk, repeated write failures), the status bar shows that recovery protection is overdue until one completes.
- **Retirement:** checkpoints are retired by writing a retirement record to the recovery folder (atomically), naming the document's identity, the session, and the edit counter it covers. A save that completes durably retires only the checkpoints at or below the edit counter that save wrote, so edits made while a save ran, and the checkpoint that holds them, stay recoverable. Closing a document cleanly or discarding its changes retires all of its checkpoints, after its pending checkpoint writes are completed or cancelled, so a late checkpoint can never resurrect discarded work. A recovered document's earlier checkpoints are retired only once its recovered contents are durable again, when a save of it or a checkpoint of it in the new session has completed, or when the user discards the recovered work; until then a crash recovers it from the earlier checkpoints again.
- **Recovery** runs at the next start, independent of how the last process ended. It first settles every save journal record left behind, resuming each save from the last durable state its journal recorded and finishing it as far as it can without deleting or overwriting anything (invariant 3): a committed save's file identity contract is completed from the previous version, a target's name left free is given the previous version back by a rename that never replaces, and every leftover file (a partial temporary file, a previous version, a foreign file at an expected name) is kept and listed in the recovery report for the user to keep or delete. A record is retired only once its save is settled: a step that cannot complete yet (a protection blocked by another program's open handle, so a committed file is still weaker than the version it displaced) keeps the record, is retried at each start and while the app runs, and the app tells the user which file is not yet protected and where the previous version is, until it completes or the user deletes the weaker file. It then scans the recovery folder for checkpoints that are neither covered by a retirement record nor owned by a running session, validates each checksum, falls back to the other slot when one is bad (and says how old that slot is), and offers each recovered document by name, untitled ones included.
- **Proofs:** the process killed at random points during edits, saves, and checkpoints (`TerminateProcess` from a test driver), and at each step of the save protocol in turn, each run checking that the target's name holds a complete old or new file and the recovered document's contents equal its newest completed checkpoint; a save of revision N that completes after revision N+1 was checkpointed, then a kill, recovering N+1; a slow save of N with a save of N+1 requested behind it, killed at each point, never leaving N on disk after N+1 committed; a cleanup failure injected after the commit point, reported as a successful save and finished at the next start; each item of the file identity contract kept through a save (a restrictive DACL inside a permissive folder, an explicit no-read-up integrity label, an EFS file shared by two users who can both still decrypt it, a compressed file, a file's Mark of the Web), and a save refused with the file untouched when another user's EFS certificate is unavailable; a checkpoint, a crash dump, the tile store's scratch after an eviction under a small cache cap, persisted undo data, and a thumbnail of an EFS-encrypted document each holding none of its plaintext after the process is killed; an untitled document recovered and the app killed before its first new checkpoint, recovered again at the next start; each of these, injected at every step of the save and of recovery, with every file kept and the user told: another program rewriting the open document's file in place, replacing it, or creating a file at the target's name between the two renames or between a crash and the next start; the same on FAT with names long enough to change file IDs; another program tightening the target's DACL, adding an EFS key holder, or encrypting the target while a save runs, the new file ending no broader than the displaced version; a kill right after the commit, before the contract (a named stream such as the Mark of the Web) was applied, completed by recovery, which keeps the previous version and lists it; a kill after the previous version is released and before the journal is retired, settled without it; a protection that cannot be applied after the commit (encryption blocked by another program's open handle), rolling the save back with no file left holding the new data; a target whose DACL grants only a logon session, the new file carrying that DACL; a first save to a new name killed at each step, leaving the complete new file or nothing; a foreign version displaced by a save, kept; power loss after each durable state, with every contract item present after restart; recovery after a kill at each step deleting and overwriting nothing and listing every leftover file, a foreign file placed at the temporary name included; another program trying, during a save, to write, rename, or delete the new file or the previous version, refused; a named stream attached to the temporary file by another program during a save, removed with it on rollback and no document data lost; a kill after a plaintext commit over a target encrypted mid-save, with another program holding the new file open through the next start, keeping the journal record, warning the user, and encrypting the file once the handle is released; that combined with encryption added mid-save and a reader blocking `EncryptFileW`, rolled back with no file left holding the new data; an external editor saving over an image Albumen shows, followed by Albumen's reload offer; a corrupted checkpoint slot; a full disk; slow writes that make the overdue notice appear; discard, save, and clean close each followed by a kill, with nothing recovered; and a kill before the first checkpoint. Power loss is proved separately, on NTFS and on ReFS (the two volumes the guarantee is stated for), with a fault harness that discards every write the storage had not made durable: the guest's disk writes and flushes are recorded below the guest, and the disk is reconstructed at every flush boundary and, between boundaries, with the writes since the last completed flush partly kept, partly dropped, and reordered (every combination where they are few, a random sample where they are many), never undoing a completed flush, as SQLite's crash tests do for incomplete and out-of-order writes, because turning a virtual machine off leaves the host's caches free to finish writes a real power loss would lose (Microsoft's Hyper-V storage caching guidance); three negative controls must fail it: a save with one required flush removed, a save that reports success before its commit and file identity contract are durable, and a checkpoint that reports completion before it is durable. Each reconstruction is booted, and after restart and recovery the check holds what the app had acknowledged before power was cut (the harness reads the log lines written before the cut) as a durability floor that a later complete commit may pass but never fall below: each target's name holds a complete version that is the newest save the app reported successful, with its contract, or a later save that committed completely; and each open document's newest acknowledged state survives: its edits up to the newest checkpoint the app reported complete are either recovered from that checkpoint or a later complete one, or held by a durable save that covered them (in which case that checkpoint was retired and nothing is offered, as the save-then-kill proof requires). The power-loss runs include that interleaving: a checkpoint completed, then a save that covers it and retires it, then power cut before the next checkpoint.

### Crash diagnostics

Collecting a dump inside a crashing process can deadlock, and the app must work for a standard user in every install mode (the per-user installer default, a per-machine install, and the portable ZIP), so dumps are collected out of process by the app itself (**Default**): at start, each app launches a small watcher (the same executable in watcher mode, nothing extra installed) that attaches to the app as its debugger (`DebugActiveProcess`, with `DebugSetProcessKillOnExit(FALSE)` so the app keeps running if the watcher ends). A dump must be taken while the crashed process still exists, and fail-fast crashes (`__fastfail`, `/GS` stack checks, `RaiseFailFastException`, heap corruption) bypass every in-process handler and reach only an attached debugger or Windows Error Reporting (Microsoft's `__fastfail` and `RaiseFailFastException` documentation), so the watcher acts on the debug events: on a last-chance exception or a fail-fast exception it writes a minidump of the still-suspended app with `MiniDumpWriteDump` and the event's exception record and thread context, encrypted as it is written through the function's I/O callbacks (Document safety, Secondary copies), so no plaintext dump touches the disk, into the app's own folder in the user's app data (the portable folder in portable mode), keeping the newest 5; the breakpoint that attaching itself raises in the app (Microsoft's `DebugActiveProcess` documentation) is continued as handled (`DBG_CONTINUE`), and every other first-chance exception is passed straight back unhandled (`DBG_EXCEPTION_NOT_HANDLED`). It needs no administrator rights and no registry settings outside the user's own. Because a process can have only one debugger, a developer switch starts the app without the watcher. Dumps can contain document data, so they never leave the machine unless the user chooses to send one from the app's Help menu, which shows what is sent and decrypts it only for that send; and so that Windows Error Reporting does not send its own report of the same crash, the app excludes itself from Windows Error Reporting for the current user (`WerAddExcludedApplication`) at first run. Every build embeds its exact version and build id, and each release's symbol files (PDBs) are archived with that id and never shipped. Proofs, as a standard user in each install mode: an access violation, a `__fastfail`, a `/GS` stack-buffer overrun, and a stack overflow each write a dump that, decrypted by the app's export, opens with the release's symbols at the faulting frame, no report appears in Windows Error Reporting's queues, a healthy start and session with the watcher attached writes no dump, and killing the watcher leaves the app running.

### The engines

Each engine is native. The pixel engine, color management, the pixel engine extensions, the develop engine, and the AI core are shared libraries by the existing operator exceptions; Stilus's vector engine (geometry, paths, and rendering through Direct2D geometry) and Albumen's catalog (SQLite) and RAW decoding (LibRaw) belong to their apps until a second app needs them.

The pixel engine's data contract carries over from its plan and is made explicit: documents store 8-bit and 16-bit integer or 32-bit float channels per the document's mode; processing runs in 32-bit float (and FP16 on the GPU only where a section measures the precision as sufficient); colors are stored with straight alpha and composited premultiplied (a deliberate replacement of the premultiplied storage that `standards/gesso.md` and `D01 T03 §1` specify today, recorded in the re-plan: premultiplied integer storage destroys color under low alpha and breaks file round trips, so straight storage keeps every channel exact; conversion to premultiplied happens only inside compositing and filters that need it, and back on commit; tests cover zero and near-zero alpha, round trips through each file format, and colors under fully transparent pixels); transfer functions follow the document's color profile, with linear-light processing where an operation requires it; extended-range values are kept in float documents and clamped only on conversion to integer modes; and the CPU, SIMD, and GPU paths agree within mode-specific tolerances per operation, checked by tests over fixed inputs (**Default**: at most 1 code value at 8-bit, at most 4 code values at 16-bit, and for float at most the larger of 2^-16 absolute and 2^-16 relative to the value, with every output finite: not-a-number and infinities are replaced at import, never produced by an operation, and a test feeds them to every operation). Tiles live in the scratch-backed tile store the plan already requires, with memory, video memory, and undo budgets set from the machine's resources; an allocation failure ends the operation with a message and leaves the document as it was.

### The apps

`stilus.exe`, `gesso.exe`, and `albumen.exe`: each a thin executable over the shared libraries and its engines, shipped on its own with its own installer, version, and update feed, as today. "Develop together, distribute separately" is unchanged.

## Dependencies and their upkeep

A library is a decision: the section that needs it adds it, records it in the dependency register (`docs/dev/native-libraries.md`) with its version, provenance, license and the URL of its license text, its advisory feed, the apps that link it, and its owning section, and it must be compatible with GPL-3.0. Linking is static, so a vulnerable library is fixed by rebuilding and releasing every app that links it: a scheduled job checks each registered library against vulnerability advisories and the vcpkg baseline. The register gives each library an advisory identity: its upstream Git repository and released tag, which the OSV database's Git queries match, or, where OSV has no record for it, the library's own advisory feed (its security advisories page or mailing list), which the job reads. A library with no identity, or a query that fails, makes the job fail, never report clean; the job's tests include a known vulnerable version (libwebp 1.3.1, CVE-2023-4863) that must be reported. A finding files a section to update, rebuild, and release the affected apps. Candidates the plan already points to, each confirmed with its license text by the section that adds it: LittleCMS 2, libpng, libjpeg-turbo, libwebp, zlib-ng, LibRaw, SQLite, spdlog, nlohmann/json, and GoogleTest. A rendering library such as Skia or Blend2D joins only for a measured need Direct2D cannot meet. SkiaSharp and AvalonDock leave with the C# code, and the AvalonDock exception in `LICENSE-EXCEPTION.md` is retired by the section that removes the last C# app.

## Testing and the gates

The proof standard in `todo/README.md` carries over, re-expressed for C++:

- **Builds clean:** Debug and Release, x64 and ARM64, warnings as errors, `/analyze` and clang-tidy clean.
- **Sanitized tests:** the whole CTest suite also runs in the AddressSanitizer configuration, with the dependencies built by the sanitizer triplet, on every architecture the pinned toolset supports AddressSanitizer for (the first sanitizer section records which) and executing on that architecture; a deliberate out-of-bounds probe test proves the lane fails when instrumentation catches an error.
- **Static analysis clean:** clang-format and clang-tidy report nothing new on the touched files.
- **Unit test:** a GoogleTest case, cited by name.
- **Driven run with evidence:** UI Automation for reading and invoking the interface, `SendInput` for the keyboard, pointer, and IME paths, a log line, a settings readback, or a saved file inspected.
- **Format fidelity proof:** fixtures opened, saved, reopened, and compared, plus each reader's fuzz target and its regression corpus.
- **Goldens:** surfaces rendered offscreen on the WARP software device in a pinned reference environment: the Windows build, the font files the design uses (Segoe UI Variable is a Windows system font we may not redistribute, so its file hashes are recorded and a golden run refuses a machine whose files differ; Cascadia Mono is licensed under the SIL Open Font License, so the golden environment loads a pinned copy bundled with the tests, under that license's conditions), fixed DirectWrite rendering parameters (antialiasing mode, gamma, contrast), a fixed DPI per golden, and a fixed locale. The first goldens section proves repeatability by rendering every golden twice, on two machines meeting the pinned environment, within the design contract's tolerance. Offscreen goldens prove drawing, not presentation, so presentation, composition, docking windows, and input keep their own driven tests on real hardware.

`scripts/check-all.ps1` runs the environment check, the CMake configure and build, CTest, the format and analysis gates, the size and import gates, and every TODO gate. CI builds x64 and ARM64 on Windows runners inside `scripts/dev-env.ps1`'s pinned environment.

## Risks and how each is held

| Risk | How it is held |
| ---- | -------------- |
| Our own toolkit takes longer than a framework would | The foundations prove the hardest pieces first, and each control is a section with a checkpoint, so progress is measured |
| Accessibility, IME, or localization gaps | Each is a foundation with driven proofs (screen reader transcripts, IME sessions, pseudo-localization and right-to-left builds) before controls are built on it |
| Memory-safety crashes or power loss losing work | The document safety failure model, its kill tests and power-loss tests that drop every unflushed write, sanitizer runs that include dependencies, and fuzzing with retained regression inputs |
| GPU driver faults | Device-loss recovery and the WARP fallback, each forced in tests |
| Wrong colors on wide-gamut or HDR displays | The display color pipeline's measured proofs in SDR and Advanced Color |
| Slower iteration in C++ | Small libraries, precompiled headers, Ninja, and unit tests that run without a window |
| A library that does not fit the 30 MB budget | The budget gate; exceeding it needs a decision entry |
| A vulnerable statically linked library | The advisory job and the rebuild-and-release section it files |
